# GB Update Tracker / FoE CDN Inspector

Discover beta content directly from the Forge of Empires game client and compare our own saved copies. New refreshes do not visit or depend on Linnun's site. Previously saved reports remain available as historical evidence.

## Refresh the Great Building dashboard

Python 3.10 or later is enough. Open or reload the [beta game](https://zz1.forgeofempires.com/) and obtain the **current** script URL containing `ForgeHX` from the page's script tags or browser developer tools. Then run:

```bash
cd foe-cdn-inspector
python3 -B -u -m foe_cdn_inspector refresh --forge-hx-url 'https://foezz.innogamescdn.com/cache/ForgeHX-…-hash.js'
```

Replace the example URL with the real one from that fresh game load. The public login page does not currently include ForgeHX. A cached URL can still download successfully after the game moves to another version, so the command deliberately requires a fresh source on every run. It never silently reuses yesterday's URL. If the game requires login, use the user's existing browser session to identify the public script URL; the collector itself does not use cookies or credentials.

Alternatively, `--client-html /path/to/fresh-game-page.html` extracts the script URL from a freshly saved game page. The local HTML is read only to identify the script; it is neither copied into results nor uploaded. Keep any game-page export containing account data private. `scan` is an alias for `refresh`.

Every refresh:

1. Verifies that the public beta bootstrap identifies market `zz`.
2. Downloads the supplied ForgeHX file directly from InnoGames, following only HTTPS redirects on the same host.
3. Reads its embedded asset map without executing JavaScript. Each asset path and fingerprint yields its exact public CDN URL.
4. Extracts literal `gettext` text, all `GBP|` bonus text literals, and names of referenced metadata groups.
5. Compares asset paths and hashes, text additions/removals, and the complete client file's SHA-256 against our previous successful scan.
6. Saves the source client and parsed inventory, then rebuilds the dashboard and its rolling 60-day archive.

The **first direct scan is a baseline**, not a release announcement. It lists all current GB bonus descriptions and icons, including older content. Dates supported by existing saved reports are retained; otherwise an item is labeled **Present at first scan**. Later dates record when our scans noticed a difference, not an official publication time. Changes made and reverted between scans cannot be recovered.

An unchanged client is downloaded and checked again, but creates no duplicate change record. Its dashboard check date advances. A malformed/incomplete download, failed beta verification, or parser failure leaves the published dashboard and latest pointer unchanged. The parser fails closed when its known client wrapper, asset-map shape, or expected text inventory no longer matches; inspect the new format and add regression coverage before retrying.

The old `strings`, `history`, and report-selection CLI commands have been retired. Current text exports and saved history are generated by the direct refresh; no external report index is needed.

## What this discovers

The complete asset map is retained, not just files with GB-related names. The GB dashboard selects bonus icons and `GBP|` descriptions from the current inventory. The change archive includes asset-reference and extracted text changes across the client, as well as a link to each changed client script. Raw client copies are saved for further code inspection. A script hash change alone does not identify a gameplay change.

**Building values, FP costs, rewards, and server rules are separate data.** ForgeHX references metadata groups such as `building_entity_lookup` and `great_building_tiers`, but the current client does not contain their full data URLs or values. Direct scans mark that coverage as **not checked**. The archive can still show building/metadata changes from older saved reports; zero new rows in those categories does not mean those values are unchanged. A future metadata collector should use actual URLs returned by the beta game's `StaticDataService.getMetadata` response, not guessed filenames.

An asset or text appearing in the client does not by itself confirm that a feature is enabled or released.

## Saved files

- `snapshots/latest.txt`: the most recent successful direct snapshot ID.
- `snapshots/<id>/direct.json`: complete asset map, extracted text, source URL/hash, metadata references, first-observed dates, and retained change records. Baseline assets can be resolved with `direct.asset_url(path, fingerprint)`.
- `snapshots/<id>/inventory.json` and `inventory.csv`: the last observed changeset, empty for the baseline.
- `snapshots/<id>/dashboard-state.json`: current text, icon inventory, archive window, and check time used to render the page.
- `.cache/forge-hx/ForgeHX-<sha256>.js`: exact downloaded client source.
- `results/gbp-current.json` and `.csv`: all currently embedded GB bonus descriptions and recorded dates, with source provenance.
- `results/history-last-60-days.json`: the rolling archive, ending on the successful check date.
- `dashboard/index.html` and `dashboard/history.html`: stable deployment files; matching dated copies remain in the snapshot.

Preserve `.cache/`, `results/`, and `snapshots/`. They are ignored local research data. Snapshots retain history outside the dashboard's 60-day view. Historical imported records are marked `legacy`; direct comparisons are marked `forge_hx`; undated initial descriptions are marked `baseline`. The old history is imported locally once, without revisiting its source website.

The header's **Data through** date means the latest successful check of the supplied client. It does not mean a new feature was released that day. Dry runs and failed checks do not advance it.

## Preview and validate

To download and compare without changing files:

```bash
python3 -B -m foe_cdn_inspector refresh --forge-hx-url 'CURRENT_PUBLIC_FORGEHX_URL' --dry-run
```

Use `--window-days` to change the archive window. Every successful refresh rebuilds the dashboard, including when the client is unchanged; a separate force option is unnecessary. To render saved data after a UI-only change without claiming a new check, use `cli.render_dashboard(snapshot_directory)`.

Serve the dashboard locally:

```bash
python3 -m http.server 8766 --bind 127.0.0.1 --directory dashboard
```

Open `http://127.0.0.1:8766/`. The larger history file loads when its archive is opened.

Successful statuses are `baseline_saved`, `refreshed`, or `up_to_date`. Check the source URL/hash, asset and description counts, history range, and coverage note. Verify that the pointer names the expected snapshot, both dashboard HTML files match it, and the string/history `failures` lists are empty. Inspect `git diff --check` and the dashboard diff. When code changes, run:

```bash
python3 -B -m unittest discover -s tests -v
```

Tests are offline and cover direct discovery, safe URL construction, snapshot differences, migration, repeat checks, failures, and the dashboard.

## Publish when requested

A refresh updates local data; it does not publish the site. When commit and push are requested, use tracker ticket `FOE-51` unless another key is supplied. Stage both `dashboard/index.html` and `dashboard/history.html`, plus the related source, tests, and documentation explicitly. Leave unrelated edits, ignored research data, and preview assets alone.

For a Git-connected Cloudflare Pages site, set project root to `foe-cdn-inspector`, output directory to `dashboard`, and no build command. The generated HTML files are tracked deployment artifacts.
